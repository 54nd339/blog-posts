The screen is a grid of squares, and a mathematical line is infinitely thin and passes between them. Drawing that line means choosing which pixels to light so the staircase of squares looks as straight as it can. This post covers that choice for lines, circles, and ellipses; how to fill the shapes once drawn; how to move, scale, and rotate them with matrices; and how to keep only the part of a scene that falls inside the window you are viewing through.

It follows the [computer graphics overview](/citadel/computer-graphics/cg) and leads into [3D graphics](/citadel/computer-graphics/3d).

## Drawing a line

A line runs between endpoints $(x_1, y_1)$ and $(x_2, y_2)$. The task is to pick the pixels closest to the ideal path.

### DDA

The **digital differential analyser** works straight from $y = mx + c$. Compute the slope $m = \Delta y / \Delta x$. If $|m| \le 1$, step $x$ by 1 each iteration and set $y_{k+1} = y_k + m$; if $|m| > 1$, step $y$ by 1 and set $x_{k+1} = x_k + 1/m$. Round the running coordinate to the nearest integer to choose the pixel.

It is easy to follow, but it uses floating-point arithmetic and the rounding error accumulates over a long line.

### Bresenham's algorithm

**Bresenham's line algorithm** uses only integer arithmetic. For a line with slope $0 < m < 1$, at each step from $x_k$ you decide whether the next pixel is $(x_k + 1,\ y_k)$ or $(x_k + 1,\ y_k + 1)$ — you never move down or backward. A **decision parameter** $p_k$ tracks which candidate is closer to the true line:

$$p_0 = 2\Delta y - \Delta x$$

At step $k$:

- If $p_k < 0$: next pixel is $(x_k + 1,\ y_k)$, and $p_{k+1} = p_k + 2\Delta y$.
- Otherwise: next pixel is $(x_k + 1,\ y_k + 1)$, and $p_{k+1} = p_k + 2\Delta y - 2\Delta x$.

Repeat $\Delta x$ times. Other slope ranges follow by symmetry — swap the roles of $x$ and $y$, or step in the negative direction. Every operation is integer addition, subtraction, or a shift (multiplying by 2), which is why it was the standard in hardware.

### In code

Both algorithms, with a check that Bresenham stays within one pixel of the exact line:

```python
def dda(x0, y0, x1, y1):
    dx, dy = x1 - x0, y1 - y0
    steps = max(abs(dx), abs(dy))
    xi, yi = dx / steps, dy / steps
    x, y = x0, y0
    pts = []
    for _ in range(steps + 1):
        pts.append((round(x), round(y)))
        x, y = x + xi, y + yi
    return pts

def bresenham(x0, y0, x1, y1):
    """Integer Bresenham for any slope / direction."""
    dx, dy = abs(x1 - x0), abs(y1 - y0)
    sx = 1 if x0 < x1 else -1
    sy = 1 if y0 < y1 else -1
    err = dx - dy
    pts = []
    x, y = x0, y0
    while True:
        pts.append((x, y))
        if (x, y) == (x1, y1):
            return pts
        e2 = 2 * err
        if e2 > -dy:
            err -= dy
            x += sx
        if e2 < dx:
            err += dx
            y += sy

# every Bresenham pixel is within half a unit of the true line
for (x1, y1) in [(10, 4), (4, 10), (-7, 3), (0, 5), (9, -9)]:
    pts = bresenham(0, 0, x1, y1)
    for (x, y) in pts:
        if x1 != 0:
            exact_y = y1 * x / x1
            assert abs(y - exact_y) <= 0.5 + 1e-9 or abs(x1) < abs(y1)
    assert pts[0] == (0, 0) and pts[-1] == (x1, y1)
```

## Drawing a circle

A circle centred at $(x_c, y_c)$ with radius $R$ satisfies $(x - x_c)^2 + (y - y_c)^2 = R^2$. It has **eight-way symmetry**: compute one point $(x, y)$ in one octant and reflect it to get the other seven, so you only calculate pixels from $x = 0$ up to $x = y$.

The **midpoint circle algorithm** carries a decision parameter, like Bresenham. Starting at $(0, R)$ with

$$p_0 = 1 - R$$

(the integer form; the exact midpoint form is $\tfrac{5}{4} - R$), at each step:

- Plot $(x_k, y_k)$ and its seven symmetric points.
- If $p_k < 0$: next point is $(x_k + 1,\ y_k)$, and $p_{k+1} = p_k + 2x_{k+1} + 1$.
- Otherwise: next point is $(x_k + 1,\ y_k - 1)$, and $p_{k+1} = p_k + 2x_{k+1} + 1 - 2y_{k+1}$.

Stop when $x \ge y$.

An **ellipse** centred at the origin satisfies $\tfrac{x^2}{r_x^2} + \tfrac{y^2}{r_y^2} = 1$ and has only four-way symmetry. The midpoint ellipse algorithm is the same idea but splits the arc into two regions — one where the slope is shallower than $-1$ and one where it is steeper — because the decision test changes when the tangent passes through $45°$.

## Filling shapes

An outline is often not enough; you want the interior coloured.

- **Scan-line polygon fill.** For each horizontal pixel row that crosses the polygon: find where the row intersects the polygon's edges, sort those intersections by $x$, and fill the spans between consecutive pairs (1st to 2nd, 3rd to 4th) using the parity rule — inside between odd and even crossings. An **edge table** and an **active edge list** make this efficient by tracking only the edges the current scan line touches.
- **Boundary fill.** Start from an interior seed pixel. If it is not the boundary colour and not already filled, colour it and recurse into its neighbours (4-connected or 8-connected). Simple, but the recursion can overflow the stack on large regions, and it needs the boundary to be a single colour.
- **Flood fill.** The same recursion, but it replaces every pixel of a specific *old* interior colour rather than stopping at a boundary colour. This is the paint-bucket tool.

## Moving shapes: 2D transformations

A transformation changes the coordinates that describe an object. The three basic ones:

**Translation** — move by $(t_x, t_y)$: $x' = x + t_x$, $y' = y + t_y$.

**Scaling** — resize by factors $(s_x, s_y)$ about the origin: $x' = x\,s_x$, $y' = y\,s_y$. To scale about another point, translate that point to the origin, scale, then translate back.

**Rotation** — turn counter-clockwise by $\theta$ about the origin:

$$x' = x\cos\theta - y\sin\theta \qquad y' = x\sin\theta + y\cos\theta$$

To rotate about another pivot, translate it to the origin, rotate, translate back.

**Reflection** mirrors a shape (across the x-axis: $x' = x$, $y' = -y$). **Shear** slants it (x-shear: $x' = x + sh_x\,y$, $y' = y$).

### Homogeneous coordinates

Scaling and rotation are matrix multiplications, but translation, written above, is a matrix *addition*. Mixing the two makes composing transformations awkward. **Homogeneous coordinates** fix this: represent the point $(x, y)$ as $(x_h, y_h, W)$ with $x = x_h / W$, and use $W = 1$, so $(x, y)$ becomes $(x, y, 1)$. Now every affine transformation is a single $3 \times 3$ matrix:

$$
T = \begin{bmatrix} 1 & 0 & t_x \\ 0 & 1 & t_y \\ 0 & 0 & 1 \end{bmatrix}
\quad
S = \begin{bmatrix} s_x & 0 & 0 \\ 0 & s_y & 0 \\ 0 & 0 & 1 \end{bmatrix}
\quad
R = \begin{bmatrix} \cos\theta & -\sin\theta & 0 \\ \sin\theta & \cos\theta & 0 \\ 0 & 0 & 1 \end{bmatrix}
$$

and a point transforms as $P' = M \cdot P$. Reflection and shear are matrices of the same form. This trick carries over to 3D with $4 \times 4$ matrices — see [3D graphics](/citadel/computer-graphics/3d). The matrix mechanics are in [linear algebra](/citadel/maths/linear-algebra); the rotation entries come from [trigonometry](/citadel/maths/trigonometry).

### Composing transformations

To apply $M_1$ then $M_2$ to a point, multiply the matrices: $P' = (M_2 M_1) P$. Precompute $M_{\text{composite}} = M_2 M_1$ once and apply it to every vertex.

Order matters. Matrix multiplication does not commute, so $M_1 M_2 \ne M_2 M_1$ in general. Translating then rotating an object gives a different result from rotating then translating — unless the rotation is about the origin.

## Framing the scene: 2D viewing

Your world may be larger than what you want to show. The viewing pipeline maps a chosen region of the world onto a region of the screen.

- **World coordinates** — the units your scene is defined in.
- **Window** (clipping window) — a rectangle in world coordinates, $(W_{x_{\min}}, W_{y_{\min}})$ to $(W_{x_{\max}}, W_{y_{\max}})$, marking what you want to see.
- **Device coordinates** — pixels on the display.
- **Viewport** — a rectangle in device coordinates where the window's contents appear.

The **window-to-viewport transformation** maps a window point $(x_w, y_w)$ to its viewport position:

$$x_v = (x_w - W_{x_{\min}})\,\frac{V_{x_{\max}} - V_{x_{\min}}}{W_{x_{\max}} - W_{x_{\min}}} + V_{x_{\min}}$$

$$y_v = (y_w - W_{y_{\min}})\,\frac{V_{y_{\max}} - V_{y_{\min}}}{W_{y_{\max}} - W_{y_{\min}}} + V_{y_{\min}}$$

This is a scale (the ratio of viewport size to window size) followed by a translation. If the window and viewport have different aspect ratios, you either distort the image or letterbox it.

### Clipping

Anything outside the window should not be drawn. **Clipping** removes it.

**Cohen-Sutherland line clipping** assigns each endpoint a 4-bit **outcode**, one bit per window boundary — top ($y > W_{y_{\max}}$), bottom ($y < W_{y_{\min}}$), right ($x > W_{x_{\max}}$), left ($x < W_{x_{\min}}$):

- **Trivial accept** — both outcodes are `0000`; the line is fully inside.
- **Trivial reject** — the bitwise AND of the outcodes is non-zero; both endpoints are outside the same boundary, so the line is fully outside.
- **Otherwise** — the line may cross the window. Take an endpoint that is outside, use its outcode to pick a boundary it crosses, compute the intersection with that boundary, replace the outside endpoint with the intersection, and repeat until the line trivially accepts or rejects.

**Sutherland-Hodgman polygon clipping** clips a polygon against one window edge at a time. Walking each polygon edge from vertex $S$ to vertex $P$:

| $S$ | $P$ | Output |
| --- | --- | --- |
| inside | inside | $P$ |
| inside | outside | intersection $I$ of $SP$ with the boundary |
| outside | outside | nothing |
| outside | inside | $I$, then $P$ |

The output vertex list from one boundary becomes the input for the next. After all four boundaries, you have the clipped polygon. This works for a convex clip window; a concave window can leave the result in disconnected pieces.

### A note on projection

Mapping from a higher dimension to a lower one is **projection**. **Parallel projection** sends rays parallel to each other and perpendicular to the view plane, preserving relative size and shape — orthographic projection is the common case, and it is implicitly what pure 2D viewing does. **Perspective projection**, where distant objects appear smaller, belongs to 3D and is the bridge to the next post.

## The one idea to keep

Two patterns run through 2D graphics. Rasterising — lines, circles, fills — is about replacing real arithmetic with an integer decision parameter you can update by addition alone. Geometry — moving, scaling, rotating, viewing, clipping — is all matrix multiplication once you add the extra homogeneous coordinate, which is the single trick that lets translation compose with everything else.
